# Fin v1 タスク状態再設計・実装計画

## 1. 現状の壊れた状態の要約（なぜv1リリースにとって重大か）

現在の実装は、見た目を比較するモックとしては成立しているが、利用者の入力を保持するタスク管理アプリとしては成立していない。中心的な問題は、`lib/tasks.ts` の `useTasks` が `app/page.tsx` のマウント中だけ存在するローカルな React state であり、ホームから `app/screen-2/page.tsx` へ移動した時点で状態の所有者がアンマウントされることである。ホームへ戻ると追加タスク、完了状態、進行中タスク、開始時刻が初期化されるため、利用者が追加したタスクは通常の完了フローを一度通るだけで消える。ハードコードされた初期タスクだけが再生成されるので、一見動作しているように見える点も危険である。

公式 v1 を App Store へ直接公開する前提では、次の問題をリリース阻害要因として扱う。

- ナビゲーションまたは再読み込みだけで利用者データが消える。これは利便性の不足ではなく、主要データの消失である。
- タイマー画面の終了時刻 `19:40` が固定値で、表示が利用者の予定を誤らせる。
- 秒数を `setInterval` で減らす方式は、バックグラウンド、端末のスリープ、ブラウザの間引き、再読み込みで実時間とずれる。0 秒でもタスクが自動完了せず、実績も残らない。
- ホームの終了予定は画面を開いた時刻から更新されず、日付境界も表現できない。
- レイアウト 1c だけタップ動作と追加機能が異なり、同一アプリ内でタスクの意味が変わる。
- 画面 3、5、6、7 は比較用表示または疑似機能で、画面 4 は存在しない。特に課金・認証を名乗るボタンが単なる `localStorage` フラグ変更なのは、公式版では信頼・審査・購入導線上の問題になる。
- 編集、削除、並べ替えがなく、長いリストは `PhoneFrame` の `overflow: hidden` で切れる。日常利用でタスクを訂正・整理できない。
- 自動テストがなく、状態遷移、永続化、時刻境界の回帰を検出できない。

したがって、画面追加より先に「タスク状態を失わない」「時刻表示が現実の時計と一致する」「疑似機能を本物として見せない」の三点を v1 の成立条件にする。

## 2. データ/状態アーキテクチャ提案（ホーム画面とタイマー画面をまたいでタスク状態を保持する方法）

### 状態の所有場所

Next.js App Router のルートセグメントをまたいで同じクライアント状態を共有するため、`app/layout.tsx` からクライアントコンポーネント `app/providers.tsx` を呼び、その中の `TaskProvider` で `{children}` を包む。`app/layout.tsx` 自体は Server Component のままにする。ホームとタイマー画面は `useTaskStore()` を通じて同じ Provider の state と action を参照し、URL の `name` や `min` をデータ本体として扱わない。タイマー画面の URL には共有・復元用ではなく識別子として `taskId` だけを置き、該当タスクがない場合はエラー状態とホームへ戻る導線を表示する。

状態更新は `useReducer` に集約し、追加、開始、一時停止、再開、手動完了、期限到達完了、編集、削除を明示的な action にする。表示用の残り時間、終了予定、割合、ラベルは保存せず、保存済み事実と現在時刻から selector の純粋関数で導出する。これによりホーム、タイマー、レポートが別々の計算を持つことを防ぐ。

### 保存するデータ

`localStorage` の新しい単一キーを `fin.task-state` とし、値は次の概念構造を持つ JSON envelope とする。時刻はローカル文字列ではなく Unix epoch ミリ秒の数値で保存する。

```ts
type PersistedTaskStateV1 = {
  schemaVersion: 1;
  savedAt: number;
  tasks: Array<{
    id: string;
    title: string;
    icon: string;
    estimateMs: number;
    subtasks: string[];
    order: number;
    status: "idle" | "running" | "paused" | "completed";
    createdAt: number;
    startedAt: number | null;
    runStartedAt: number | null;
    deadlineAt: number | null;
    remainingMsAtPause: number | null;
    accumulatedActiveMs: number;
    completedAt: number | null;
    completionReason: "manual" | "elapsed" | null;
  }>;
  activeTaskId: string | null;
};
```

`startedAt` は最初に開始した時刻、`runStartedAt` は現在の連続稼働区間の開始時刻、`deadlineAt` は稼働中の絶対終了時刻、`accumulatedActiveMs` は過去の稼働区間の合計である。一時停止中だけ `remainingMsAtPause` を持つ。完了タスクも同じ配列に残すため、画面 5 は `estimateMs` と実績時間を集計できる。`activeTaskId` と各 task の status は復元時に整合性検査し、同時に複数の `running` task が存在しないよう reducer の不変条件にする。

初期タスクは `SEED` として毎回結合せず、保存データが一度も存在しない初回だけ state 生成時に投入する。これにより、初期タスクを削除・完了した後に復活する問題を防ぐ。`fin-onboarded` と `fin-pro` はタスク状態とは別の既存キーだが、後述の画面整理で疑似 Pro フラグは廃止し、オンボーディング状態は必要なら `fin.preferences` のような別のバージョン付き envelope へ移す。

### 読み込みと保存

Provider はクライアントで初回マウント後に `localStorage` を読み、検証・マイグレーション・期限切れタイマーの整合を行ってから `hydrated` にする。復元前に初期タスクを一瞬表示して上書きしないよう、ホームとタイマーは hydration 完了まで専用の読み込み状態を表示する。以後は reducer の確定した状態変更ごとに同期保存する。`storage` event も購読し、同一端末の別タブで更新された場合は、`savedAt` が新しい正常な envelope のみ取り込む。

JSON 破損、型不正、未対応の将来バージョンではクラッシュさせない。元値を同じセッション中に上書きせず、復元失敗の案内と「新規状態で始める」操作を出す。利用者が明示的に初期化を選んだ場合だけ壊れた値を退避キーへ移して新規作成する。`localStorage` の容量超過時は state をメモリ上で動かし続けつつ「この端末に保存できていない」ことを表示し、成功したように黙らない。

### バージョニングとマイグレーション

読み込み処理は `schemaVersion` ごとの `v1 -> v2` のような一方向の純粋 migration と runtime validation を通す。現在はタスク本体の旧保存形式が存在しないため、初回の v1 は「キーなしなら初期タスクを一度だけ生成」でよい。既存の `fin-onboarded` は画面 7 を簡略化するフェーズで新しい設定キーへ一度だけ変換できる。将来のフィールド追加では、既定値を埋めた後に最新版として保存し直す。未知の高いバージョンを古いアプリで勝手に変換・上書きしない。

現時点ではバックエンドを前提にしない。単一端末、単一インストール内の v1 なら、バージョン付き `localStorage` で今回のデータ消失問題を解消できる。端末間同期、アプリ削除後の復元、アカウント連携が v1 要件なら、認証・バックエンド・プライバシー設計が別途必要になるため、セクション 7 のオーナー判断事項とする。

## 3. リアルタイムに正しいタイマー/終了時刻計算のモデル提案

### 個別タスクの計算

タイマー開始時に `now = Date.now()` を一度取得し、初回なら `startedAt = now`、常に `runStartedAt = now`、`deadlineAt = now + remainingBeforeStart` とする。画面が表示する残り時間はカウンタ state ではなく、描画更新のたびに次で求める。

```ts
remainingMs = Math.max(0, deadlineAt - now)
```

1 秒間隔の tick は画面を再描画するためだけに使い、正しい値の情報源にはしない。tick が遅延しても次回描画時に `Date.now()` との差へ戻る。一時停止時は `remainingMsAtPause = max(0, deadlineAt - now)` と、現在区間の実績を `accumulatedActiveMs += now - runStartedAt` に確定し、`runStartedAt` と `deadlineAt` を `null` にする。再開時は `deadlineAt = now + remainingMsAtPause` として新しい絶対時刻を作る。

実績時間は、稼働中なら `accumulatedActiveMs + (now - runStartedAt)`、一時停止または完了済みなら `accumulatedActiveMs` とする。手動完了時は現在区間を加算して `completedAt = now`、`completionReason = "manual"` にする。期限到達時は残りを 0 とし、`completedAt = deadlineAt`、`completionReason = "elapsed"`、実績を見積時間まで確定する。同じ完了 action が複数回走っても二重記録されないよう冪等にする。

### バックグラウンド化・再読み込み・0 秒到達

`visibilitychange`、`focus`、Provider の hydration、通常の表示 tick の各タイミングで `reconcileTimers(now)` を呼ぶ。保存された `running` task の `deadlineAt <= now` なら、その場で期限到達完了へ遷移して永続化する。バックグラウンド中に通知を保証することはこの Web 実装の範囲外だが、復帰時の状態と時刻は必ず正しくなる。

0 秒到達時は対象タスクを自動完了し、完了演出を一度だけ表示した後にホームへ戻す。利用者が完了ボタンを同時に押しても reducer の冪等性で履歴は一件だけにする。再読み込み後も `taskId` から永続 state の対象を引けるため、タイマーを継続または期限到達完了へ整合できる。一時停止中の再読み込みでは残り時間は減らさない。

端末時計が手動変更された場合、絶対時刻方式は新しい端末時計に従う。大幅な後退を検知したときに自動で時間を増やすのではなく、保存時刻との差が不自然である旨を表示する案もあるが、v1 の必須範囲には含めない。

### ホーム全体の終了予定

ホームの残り時間は次の合計から求める。

- 稼働中タスク: `max(0, deadlineAt - now)`
- 一時停止中タスク: `remainingMsAtPause`
- 未開始タスク: `estimateMs`
- 完了タスク: `0`

稼働中なら `overallFinishAt = now + totalRemainingMs` とする。一時停止中は時刻が確定しているように見せず、「一時停止中」「今再開した場合は 19:40」のように表示する。全タスク未開始の場合は「今から始めた場合」の終了予定として同じ式を使う。ホームを開いたままでも最低 30 秒ごと、加えて `focus` と `visibilitychange` で `now` を更新する。個別タイマー画面だけは秒表示のため 1 秒ごとに再描画する。

日付をまたがない場合は `19:40`、翌日なら `翌日 0:20`、それより先なら `8月4日 0:20` のように日付を含める。計算は epoch ミリ秒、表示は端末のローカルタイムゾーンを使う。`24:20` のような存在しない時刻や、単純な 24 時間剰余だけの表示は使わない。

## 4. 各モック/未完成画面（3, 存在しない4, 5, 6, 7）と1cレイアウトの不整合について、それぞれ具体的な推奨

| 対象 | 推奨 | 理由 |
|---|---|---|
| 画面 3 | **v1 スコープから外す。** 完了演出の比較用途は製品ルートから除き、採用した一種類の演出だけを画面 2 に残す。比較資産を保持するなら開発専用 Storybook 等へ移す。 | ソース自身が比較プレビューと明記しており、利用者の実データと接続する製品画面ではない。複数案選択 UI は主要フローを曖昧にする。 |
| 画面 4 | **新規作成しない。** 画面番号への参照があれば削除し、製品仕様では意味のあるルート名を使う。 | 欠番を埋めること自体に利用者価値がない。番号ベースのモック構造を製品 IA として固定しないため。 |
| 画面 5 | **本実装する。** 完了履歴から見積時間帯ごとの件数、平均実績、差分を集計し、記録が少ない場合は正直な空状態を出す。v1 では無料機能として扱うことを推奨する。 | Fin の価値である見積もり改善に直結する一方、現在の固定サンプルは実績を装っていて誤解を招く。課金基盤なしで Pro 専用を名乗るべきではない。 |

| 画面 7 | **簡略化して正直なオンボーディングとして本実装する。** ボタンを「Fin を始める」へ変更し、Apple ロゴインやアカウント作成を示さず、端末内保存であることを説明する。 | v1 がクライアントのみなら認証は不要であり、単なるフラグ設定を Sign in with Apple と表示してはいけない。実認証が事業要件なら別途オーナー承認と設計が必要。 |

固定 393×852 の `PhoneFrame` はデザイン比較用の枠であり、製品画面のコンテナとしては使わない。ホームは実 viewport に追従させ、ヘッダーと追加ボタンを固定する場合でも、タスクリスト領域には `overflow-y: auto`、適切な下余白、safe-area 対応を持たせる。短い画面、文字サイズ拡大、10 件以上のタスクでも最後の行と追加操作へ到達できることを条件にする。

## 5. フェーズ分けした実装順序

各フェーズは、その終了時点で動作確認でき、次フェーズを待たずに前フェーズの改善だけをリリースできる単位とする。実装開始時には、そのフェーズの所有ファイルだけを登録し、進行中の別作業と競合する場合は先に統合または待機する。

### フェーズ 1: タスク state の単一化と端末内永続化

**目的:** ナビゲーションと再読み込みでタスクが消える最優先障害を解消する。

**実装内容:** バージョン付き永続型、runtime validation、migration、reducer、selector、`localStorage` adapter を純粋ロジック中心に分離する。`TaskProvider` をルート layout 配下へ置き、ホームと画面 2 が同じ task を ID で参照するようにする。初回だけ初期タスクを投入し、以後は追加・完了状態を保存する。このフェーズではタイマーの精密化は行わず、画面 2 からの手動完了が共有 state に直接反映されるところまでに限定する。

**触るファイル:** `app/layout.tsx`、新規 `app/providers.tsx`、`app/page.tsx`、`app/screen-2/page.tsx`、`lib/tasks.ts`、新規 `lib/task-state.ts`、新規 `lib/task-storage.ts`、`components/TaskRow.tsx`、テストランナー導入を同時承認する場合は `package.json`、`package-lock.json`、新規 `vitest.config.ts`、新規 `lib/task-state.test.ts`、新規 `lib/task-storage.test.ts`。

**フェーズ終了時に動くこと:** 追加したタスクを開始してホームへ戻っても消えず、完了状態が反映される。ページ再読み込み後もタスク一覧と完了状態が復元される。壊れた保存データで白画面にならない。

### フェーズ 2: 絶対時刻ベースのタイマーと終了予定

**目的:** 個別タイマーとホームの終了予定を端末時計に対して正しくする。

**実装内容:** 開始・一時停止・再開・手動完了・期限到達完了 action を実装し、`deadlineAt` から残り時間を導出する。Provider で hydration、focus、visibility 復帰時の reconciliation を行う。画面 2 の固定 `19:40` とクエリ由来の名前・分数を廃止し、共有 task と selector の値だけを表示する。ホームの `start` 固定 state と `addMinutes` 依存を廃止し、現在時刻から全体終了予定を再計算する。日付越えラベルを追加する。

**触るファイル:** `lib/task-state.ts`、新規 `lib/task-time.ts`、`app/providers.tsx`、`app/page.tsx`、`app/screen-2/page.tsx`、`components/timer/TimerBar.tsx`、`components/timer/TimerNumeric.tsx`、`components/timer/TimerRing.tsx`、`components/layouts/StackedTop.tsx`、`components/layouts/CenteredSheet.tsx`、テスト導入済みなら新規 `lib/task-time.test.ts` と `lib/task-state.test.ts`。

**フェーズ終了時に動くこと:** バックグラウンドや再読み込みを挟んでも残り時間が実時間と一致し、0 秒で一度だけ自動完了する。一時停止中は減らず、再開後に正しい期限を持つ。ホームと画面 2 が同じ終了時刻を示し、翌日表示も正しい。

### フェーズ 3: ホームを単一の製品 UI に整理し、日常的なタスク操作を成立させる

**目的:** 比較モックではなく、長い一覧を安全に扱える一貫したホーム画面にする。

**実装内容:** 1a を製品レイアウトとして固定し、1a/1b/1c 切替ツールバーを外す。`PhoneFrame` 依存をホームから外して viewport と safe-area に対応し、タスクリストをスクロール可能にする。追加導線を常時到達可能にする。タスク編集・削除を v1 に含めることが承認された場合は、既存追加シートを追加・編集共用へ拡張し、実行中タスク削除時には確認を要求する。並べ替えはオーナー判断がなければ v1 では見送り、`order` は追加順を保持するためだけに使う。

**触るファイル:** `app/page.tsx`、`components/layouts/StackedTop.tsx`、`components/TaskRow.tsx`、`components/TaskAddSheet.tsx`、`components/PhoneFrame.tsx`、`lib/task-state.ts`、編集 UI を分ける場合は新規 `components/TaskEditSheet.tsx`。1b/1c の製品切替を完全撤去する承認がある場合は `components/layouts/CenteredSheet.tsx` と `components/layouts/FullBleed.tsx` も整理対象にする。

**フェーズ終了時に動くこと:** 小さい端末、文字サイズ拡大、長い一覧でも全タスクと追加ボタンへ到達できる。未完了タスクのタップは常にタイマーを開き、同じ操作がレイアウトによって即完了へ変わらない。承認範囲に応じて、入力ミスを編集または削除で訂正できる。

### フェーズ 4: 完了履歴と実データのレポート

**目的:** 固定サンプルを廃止し、利用者自身の見積もりと実績だけを表示する。

**実装内容:** 完了 task の `estimateMs`、`accumulatedActiveMs`、`completedAt` を selector で集計する。見積時間帯ごとの件数、平均実績、平均差分を算出し、記録 0 件または少数件の空状態を用意する。自動完了と手動完了を同じ一件として扱い、一時停止時間は実績へ含めない。履歴保持期間のオーナー判断を反映し、期間外データの削除を行う場合は利用者への説明と明示的な方針を持たせる。Pro ロックは設けず、v1 の実機能としてホームから開けるようにする。

**触るファイル:** `app/screen-5/page.tsx`、`app/page.tsx`、新規 `lib/task-report.ts`、`lib/task-state.ts`、テスト導入済みなら新規 `lib/task-report.test.ts`。

**フェーズ終了時に動くこと:** 完了記録がない利用者には空状態が表示され、記録がある利用者にはその実データだけから集計した値が表示される。固定の「平均 28 分」などは一切表示されない。

### フェーズ 5: 疑似認証・疑似課金・比較画面のリリース面からの除去

**目的:** App Store へ出す製品導線を、実装済み機能と正直に一致させる。

**実装内容:** 画面 7 を「Fin を始める」オンボーディングへ変更し、端末内保存であることを説明する。ホームから画面 6 への Pro 分岐と `fin-pro` の読み書きを外す。画面 3 と画面 6 は v1 のナビゲーション、サイトマップ、利用者導線から除外する。ファイル削除はオーナー承認が必要なため、承認前は製品から到達不能にし、直 URL では「この機能は現在提供していません」とホーム導線だけを出す。承認後は不要ルートを削除する。画面 4 は作らず、画面番号を利用者向けコピーや設計名称から外す。

**触るファイル:** `app/page.tsx`、`app/screen-7/page.tsx`、`app/screen-3/page.tsx`、`app/screen-6/page.tsx`、`lib/task-storage.ts`。削除承認後は `app/screen-3/page.tsx`、`app/screen-6/page.tsx` と、採用されなかった完了演出コンポーネントが削除候補になる。

**フェーズ終了時に動くこと:** 初回利用者は認証と誤解せず開始でき、アプリ内に偽の登録・購入成功状態がない。通常操作から比較用画面へ迷い込まず、存在しない画面 4 への期待も生まれない。

### フェーズ 6: v1 リリース候補の回帰確認と状態回復 UX

**目的:** 直接公式公開する候補を、主要フローと異常系の両方で固定する。

**実装内容:** 自動テストランナーが未導入ならこのフェーズまでに導入し、reducer、migration、時刻、レポートの純粋関数を自動化する。主要な画面遷移はブラウザ E2E を追加するか、少なくとも固定の手動チェックリストをリリース判定資料として実施する。保存失敗、壊れた JSON、未知バージョン、存在しない task ID の利用者向け表示を最終確認する。実装変更が必要な不具合だけを、該当責務のファイルへ小さく戻して修正する。

**触るファイル:** `package.json`、`package-lock.json`、`vitest.config.ts`、`lib/*.test.ts`、E2E を採用する場合は新規 `playwright.config.ts` と新規 `tests/e2e/task-flow.spec.ts`。回復表示の修正が必要な場合のみ `app/providers.tsx`、`app/page.tsx`、`app/screen-2/page.tsx`。

**フェーズ終了時に動くこと:** 追加、開始、一時停止、復帰、期限完了、手動完了、再読み込み、履歴集計の一連の流れが再現可能な証拠付きで通る。保存異常でも白画面や無言のデータ初期化にならない。

## 6. フェーズごとの簡単なテスト戦略

現時点で自動テストは存在しないため、各フェーズで最低限の手動確認を必須とし、純粋関数から順に自動化する。自動テスト導入を承認する場合はフェーズ 1 から Vitest 等を入れる方が回帰コストは低い。導入を後ろ倒しする場合でも、手動結果を記録し、フェーズ 6 で同じ観点を自動化する。

| フェーズ | 最低限の手動確認 | 自動テスト化する価値が高いもの |
|---|---|---|
| 1 | 新規タスクを追加し、タイマー画面へ移動して戻る。完了後に戻る。ホーム、画面 2 の両方で再読み込みする。別タブで更新する。壊れた JSON を読み込ませ、白画面と無言初期化にならないことを確認する。 | reducer の各 action と不変条件、初回 seed が一度だけ入ること、v1 の encode/decode、破損値・未知バージョン拒否、storage event の新旧判定。 |
| 2 | 30 秒程度のタスクで開始、一時停止、再開、手動完了、0 秒自動完了を確認する。タブをバックグラウンドにし、期限後に復帰する。途中で再読み込みする。23:59 付近相当の日付越え表示を確認する。 | fake clock による残り時間、pause/resume、複数回完了の冪等性、hydration 時の期限切れ reconciliation、翌日・翌々日の表示、ホームとタイマーの終了時刻一致。 |
| 3 | 320px 相当の幅、短い高さ、200% 文字拡大、10〜30 件の一覧で最後の行と追加操作へ到達する。全ての未完了行がタイマーを開くことを確認する。編集・削除を採用した場合は実行中タスクの削除確認も行う。 | add/edit/delete action、order の安定性、実行中 task 削除の拒否または確認後動作。UI は主要 viewport の E2E またはスクリーンショット比較。 |
| 4 | 完了 0 件、1 件、複数の見積時間帯、手動完了、自動完了、一時停止を含む履歴で表示値を電卓計算と照合する。 | 集計の grouping、平均と丸め、pause 除外、空状態、保持期間境界、同一完了の重複排除。 |
| 5 | 新規ストレージで起動し、「Fin を始める」からホームへ進む。通常導線に Sign in with Apple、Pro 登録、比較画面、画面 4 がないことを確認する。旧 `fin-onboarded` 所有者も再オンボーディングされないことを確認する。 | 旧オンボーディングキーの一回限り migration、主要 route の到達可否、製品コピーに禁止した認証・課金表現が残っていないこと。 |
| 6 | 新規利用、既存利用、壊れた保存、容量不足相当、存在しない `taskId` を通す。対応対象の実機またはラッパー環境でバックグラウンド復帰と safe-area を確認する。 | reducer・migration・clock・report の全関連 suite、追加→開始→再読み込み→期限完了→レポートの E2E、型チェック、lint、production build。 |

リリース候補では、単に build が通るだけでなく「利用者が入力したデータが各遷移後も同一であること」と「画面に出した時刻を保存事実と端末時計から再計算できること」を合格条件にする。

## 7. オーナーの判断が必要な未決事項の明示的な列挙

1. 完了タスク履歴は無期限保持、一定期間保持、日次リセットのどれにするか。日次リセットなら、暦日境界のタイムゾーンと削除前の確認・書き出しは必要か。
2. タスクの編集と削除を公式 v1 の必須範囲に含めるか。本計画は日常利用上の訂正手段として含めることを推奨する。実行中タスクの削除は許可するか、先に停止・完了を必須にするか。
3. タスクの並べ替えを v1 に含めるか。本計画の既定推奨は追加順固定で、ドラッグ並べ替えは v1 後である。
4. 初回に現在の 6 件の seed タスクを実データとして作成するか、空の一覧と作成ガイドから始めるか。一度作成した seed をアプリ更新で再投入しない方針は共通とする。
5. v1 の正式ホームは 1a 固定でよいか。1b を採用する場合はどちらか一方を選び、製品内のレイアウト比較 UI は外してよいか。
6. 画面 3、画面 6、採用されないレイアウト・完了演出のソースファイルを削除してよいか。それとも開発用プレビューとして製品ルート外へ保持するか。削除は別途明示承認が必要である。
7. 画面 5 の実績レポートを無料の v1 機能として提供してよいか。将来 Pro 化を検討する場合、既存利用者の扱いをどうするか。
8. v1 に本物の Sign in with Apple が必要か。不要なら画面 7 を端末内オンボーディングへ変更する。必要なら認証、アカウント削除、プライバシー表示、データ同期を含む別の高リスク設計・実装を先に承認する必要がある。
9. v1 に有料 Pro サブスクリプションが必要か。不要なら疑似 Pro 導線を完全に外す。必要なら価格、無料期間、購入復元、解約案内、レシート検証、権利状態、App Store Server Notifications を含む別計画が必要である。
10. 単一端末の `localStorage` 保存で v1 要件を満たすか。アプリ削除後の復元、複数端末同期、Web とネイティブ間同期のいずれかが必要なら、バックエンドを前提にせず要件を確定してから方式を選ぶ必要がある。
11. App Store 版の実行形態は WebView ラッパー、PWA 相当、別のネイティブ構成のどれか。バックグラウンド通知、保存領域の寿命、safe-area、審査要件の検証対象が変わるため、フェーズ 6 前に確定が必要である。
12. タイマー期限到達時にローカル通知や音を必須とするか。画面復帰時の正しい整合は本計画に含むが、バックグラウンド中の確実な通知は別のプラットフォーム権限・実装が必要である。
13. 端末時計を大幅に変更した場合に警告を出すか。v1 は端末時計を正として再計算する方針でよいか。
14. テストランナーをフェーズ 1 から導入するか、フェーズ 6 でまとめて導入するか。本計画は時刻と migration の回帰リスクからフェーズ 1 導入を推奨する。
